# 運用

[English](../en/operations.md) | 日本語

日常の運用で行う変更は、主にノイズの除外条件の追加、L2 の新規作成と作り替え、L3 の追加です。
L1 は LogEntry の共通項目を列に、個別の内容を属性に保存するため、ログの種類が増えても L0 と L1 を作り直すことはほとんどありません。
L0 と L1 の作り直しと切り替えは、復旧や構成の見直しのときだけ使うので、付録に分けています。

各手順の SQL ひな型は `sql/runbooks/` にあります。
このページでは、手順ごとの前提と、実機で確かめた注意点を説明します。
数値と条件は [検証記録](findings.md) にあります。

## 日常の確認

パイプの状態表示は、Failed になるまで処理の停滞を示しません。
次の項目を `verify/checks.sql` で定期的に確かめます。

| 確認項目 | `verify/checks.sql` | 異常の目安 | 対処 |
|---|---|---|---|
| 経路全体の欠損 | 9 番と Cloud Monitoring の `logging.googleapis.com/exports/log_entry_count` | シンクの送出件数との差が 1% を超える（平常時は 0.1% 未満） | パイプの状態、Pub/Sub の滞留、シンクの送出エラーを確かめる |
| 処理が停滞したバッチ | 2 番 | 0 より大きい | 「MV のエラーの検知と復旧」 |
| 失敗した INSERT | 6 番 | 1 件以上 | 「MV のエラーの検知と復旧」 |
| 取り込みの遅れ | 1 番 | p99 が 10 秒を超えて増え続ける | パイプのレプリカを増やす。Pub/Sub の未処理メッセージの経過時間も見る |
| 重複 | 3 番 | 障害や一時停止の後に増えた | 検索側で除くか、付録 A2 で該当日を作り直す |
| パイプの状態 | `clickhousectl cloud clickpipe get` | Failed | 「MV のエラーの検知と復旧」 |

```bash
export CH_SERVICE_ID=<service id>
python3 tools/chq.py verify/checks.sql
```

## 手順の選び方

| 目的 | 手順 | SQL | パイプの停止 |
|---|---|---|---|
| 大量に発生し、個別に確認する必要性が低いログを外す | ノイズの除去と、ログの種類に依存しない整形 | `sql/runbooks/07_add_noise_rule.sql` | 不要 |
| L1 で満たせない要件のあるログを型付きの列にする。既存の L2 を作り替える | L2 の新規作成と作り替え | `sql/runbooks/08_add_or_rework_l2.sql`、例 `sql/examples/` | 不要 |
| 長い期間の推移を速く見る。集計だけ長く残す | L3 の追加 | `sql/runbooks/09_add_l3.sql`、`09_add_l3_backfill.sql` | 不要 |
| MV が例外を出している。パイプが Failed になった | MV のエラーの検知と復旧 | `sql/runbooks/05_mv_failure.sql` | ― |
| 取り出す列を増やす | 付録 A1 | `sql/runbooks/01_add_column.sql` | 不要 |
| 解析の誤りを直し、過去日も直す | 付録 A2 | `sql/runbooks/02_rebuild_partition.sql` | 不要 |
| 型、ORDER BY、パーティション、エンジンを変える | 付録 A3 | `sql/runbooks/03_blue_green.sql` | 不要 |
| パイプの設定を変える（作成後に変えられないもの） | 付録 A4 | `sql/runbooks/04_pipe_swap.sql` | 不要（並走） |
| `_publish_time` を持たない既存の取り込みから移る | 付録 A5 | `sql/runbooks/06_migrate_legacy_pipeline.sql` | 不要（並走） |

多くの手順で「境界時刻 T」を使います。
T は `_publish_time`（Pub/Sub の公開時刻）で決め、作業時刻の数分先にします。
T より前と T 以降を新旧の MV で分担するので、取りこぼしも二重取り込みも起きません。

## 「無停止」の定義

読み取り、取り込み、完全性を分けて扱います。

| 目標 | 意味 | 本サンプルの手順で確かめた範囲 |
|---|---|---|
| 読み取り継続性 | ClickStack と SQL の検索が止まらない | 読み取り先の切り替えはビューの置き換えかソース設定の変更で行い、停止はない |
| 取り込み継続性 | ClickPipe を止めない | 列追加、パーサ修正、Blue/Green、パイプ差し替えのいずれも、パイプを止めずに完了した |
| 完全性 | 受け取ったメッセージを失わず、二重に数えない | 送信した全メッセージ ID と L1 を突き合わせ、欠損 0、`MessageId` の重複 0 を確認した |

完全性の確認は、L0 と Pub/Sub トピックの保持期間に残っている範囲でしか行えません。
保持期間を過ぎたデータは、作り直しも照合もできなくなります。

## ノイズの除去と、ログの種類に依存しない整形

### ノイズは MV で除外し、件数だけ残す
大量に発生し、個別に確認する必要性が低いログは、MV1 の `WHERE` で L1 から外すのを基本にします。
同じ条件の行を、別の MV（`sql/50_noise_rollup_v1.sql`）で分ごとの件数として残します。
どのログがノイズになるかは環境で変わります。
検証環境では Kubernetes の Lease 更新の監査ログでした。
除外条件を追加する手順のひな型は `sql/runbooks/07_add_noise_rule.sql` です。

- L0 には生の行が保持期間のあいだ残るので、除外条件を取り消す場合は、L0 から作り直せます。
- 件数は残るので、更新が止まった（コントローラーが停止した）ことはグラフで見えます。
- Pub/Sub と ClickPipes の転送量は減りません。Cloud Logging 側にも残り（`_Required` 行きなど）、量が多く、ClickHouse で検索しないログは、シンクのフィルタで除外する選択肢もあります。その場合は件数も残りません。検証環境の Lease 更新は、Pub/Sub に送った量の 59% でしたが、金額ではクラスタ 1 つあたり月に約 $4 でした（[検証記録](findings.md)）。

除外条件の切り替えには、ほかの手順と同じく `_publish_time` の境界 T を使います。
集計の MV は `_publish_time >= T` の行だけを数え、MV1 は `_publish_time >= T` の行だけを外します。
検証では、境界以降に集計された件数（1,940）と、L0 にある同じ条件の行の数（1,940）が一致し、L1 には 0 件でした。

### ログの種類に依存しない整形は MV1 に入れる
- JSON のキーが `msg` のログ（istio、cilium など）は、`message` がなければ `msg` を Body にする。
- `key="value"` 形式の本文（klog や logfmt）は `extractKeyValuePairs` で分解し、`kv.*` 属性に入れる。`latency` は `kv.latency_ms` としてミリ秒にも直す。

GKE のコンテナログは、ログ収集の段階で JSON の `level` が重大度に変換されていたので、重大度を整形する必要はありませんでした。

## L2 の新規作成と作り替え

L2 は任意です。
次の条件のいずれかに該当する場合にのみ作成します。
どれにも該当しなければ、L1 で検索し、値を取り出して表やグラフにします。

| L2 を作る判断基準 | L2 の前に試すこと |
|---|---|
| 日常的に使う画面で、L1 での応答が目標時間（例：数秒）を超える（L1 の読み取り量は対象期間の行数で決まる） | 対象期間を短くする。L3 の集計を使う |
| 特定の列（監査ログの操作者、ノードプールなど）で頻繁に絞るのに、L1 の並び順では読み取り量が減らない | その値を L1 の並び順に含まれる列（ServiceName など）で表現できるか検討する |
| 時刻や数値の計算を毎回の検索で記述する負担が大きい、または間違えやすい。アラートの条件に使う | ダッシュボードのタイルに式を一度だけ書く |
| 保持期間、閲覧権限、削除の扱いを種類ごとに分けたい | なし（L2 で分ける） |
| 重複を除いた結果や、最新の状態だけが欲しい | 検索時に `LIMIT 1 BY` を使う |

一度きりの調査、量の少ないログ、内容の形式が安定していないログには作りません。
先に L1 だけで同じ表やグラフを作り、L2 がそれと同じ結果を返すことを確かめます。

**新規作成**

1. 型付きテーブルと、L0 から該当ログだけを読む MV を作る（MV は `_publish_time >= T`）。
2. T を過ぎたら、T より前の分を L0 から `LIMIT 1 BY _message_id` でバックフィルする。
3. ClickStack にログソースとして登録し、ダッシュボードのタイルの参照先を切り替える。

L2 は L0 を読むので、MV1 のノイズの除外条件を L2 の MV にも書きます。
L1 には手を付けないので、全体の検索には影響しません。

**再構築**（列の追加、並び順の変更）

1. 版番号を上げた名前で、新しいテーブルと、L0 から読む境界付きの MV を作る（`_publish_time >= T`）。
2. T より前の分を L0 からバックフィルする。L0 に残っていない古い分は、旧 L2 から、L0 の最古の公開時刻より前の範囲だけを、列を変換して写す。
3. ClickStack のソースを新しいテーブルに切り替える。ロールバック期間を過ぎたら、旧 MV と旧テーブルを削除する。

手順のひな型は `sql/runbooks/08_add_or_rework_l2.sql`、例は `sql/examples/l2_audit_events_v1.sql`（ハンズオンで使う）と `sql/examples/l2_gke_upgrades_v1.sql` です。
L2 は L0 から作るので、遡れるのは L0 の保持期間の分だけです。
それより古い分は、作り替えのときに旧 L2 から、L0 の最古の公開時刻より前の範囲だけを写します。

## L3 の追加

長期間の推移を示すグラフを高速化したい場合や、個々のログより集計結果を長く保持したい場合に、L1 や L2 を元に集計テーブル（L3）を追加します。
`sql/40_rollup_1m_v1.sql` の分単位の件数も L3 の一つです。

1. 集計テーブルと、L1（または L2）から読む MV を作る（MV は `PublishTime >= T`）。
2. T を過ぎたら、T より前の分を同じ GROUP BY の `INSERT ... SELECT` でバックフィルする。
3. 新しいデータが追加されない範囲で、L3 の合計と元の表の件数が一致することを確かめる。
4. ClickStack の SQL タイルの参照先を L3 に切り替える。

MV は INSERT のときしか動かないので、過去分は同じ GROUP BY の `INSERT ... SELECT` でバックフィルします。
元の表でパーティション操作（付録の手順）をしたときは、L3 の同じ範囲も作り直します。
手順のひな型は `sql/runbooks/09_add_l3.sql`（集計テーブルと MV）と `sql/runbooks/09_add_l3_backfill.sql`（T を過ぎてから実行するバックフィルと照合）です。

## MV のエラーの検知と復旧

MV が例外を出したときの挙動は、次のとおりでした。

1. 失敗したバッチは L0 には書かれ、L1 には届かない。
2. パイプは同じバッチを 10 秒、30 秒、70 秒、その後は 2 分ごとに再試行する。
3. ほかのバッチは並行して処理され、パイプの状態は短時間 Degraded になった後 Running に戻る。エラーテーブルには行が書き込まれない。
4. `MODIFY QUERY` で MV を直すと、次の再試行で L1 に届き、欠損も重複も出ない。

4 は、L0 でブロックの重複が排除されたうえで、下流の MV にはブロックがもう一度渡されるためです。
これは ClickHouse Cloud の既定値 `deduplicate_blocks_in_dependent_materialized_views = 1` によります。

ただし検証では、最初の失敗から約 60 分たつと、パイプは Failed になって取り込みを止めました。
その場合も、MV を直してから `clickpipe start` で再開すれば欠損は出ませんでしたが、処理が停滞したバッチの一部が L1 に二重に入りました。
再開後は `verify/checks.sql` の 3 番で `MessageId` の重複を確かめ、検索側で除くか、該当範囲を付録 A2 で作り直します。

パイプの状態表示は、Failed になるまで処理の停滞を示さないので、監視は L0 と L1 の差と、`system.query_log` の失敗した INSERT で行います。
SQL は `sql/runbooks/05_mv_failure.sql` にあります。

MV は DROP して作り直さず、`MODIFY QUERY` で直します。
DROP と CREATE の間に INSERT されたブロックは、MV を通らずに L0 にだけ残ります。

## 避ける操作

| 操作 | 26.6.1 で観察した結果 |
|---|---|
| MV の書き込み先を `EXCHANGE TABLES` | MV は元の物理テーブル（交換後は別の名前）に書き続けた |
| MV の読み取り元を `EXCHANGE TABLES` | MV は名前に追従し、新しくその名前を持ったテーブルへの INSERT で発火した |
| MV の読み取り元を `RENAME TABLE` | 旧名と新名のどちらへ INSERT しても、MV はエラーを出さずに発火しなくなった |

ClickHouse の版によっては、`EXCHANGE` の後に MV が発火しなくなる不具合もありました（[ClickHouse#105021](https://github.com/ClickHouse/ClickHouse/issues/105021)）。
`EXCHANGE` を使ってよいのは、MV にもパイプにもつながらない参照専用のテーブルに限ります。

このほか、MV を DROP して作り直す操作（その間の INSERT が MV を通らない）、MV の SELECT をそのまま `INSERT ... SELECT` に使う操作（列が位置で対応付けられて値がずれる）、L0 を重複除去なしで作り直しの元にする操作（再配信の重複が L1 に戻る）も避けます。

## リソースの削除

- 止めたパイプの管理サブスクリプションは残り、メッセージが蓄積し続けます。使わないパイプは削除します。
- パイプを削除しても、宛先テーブルとエラーテーブルは残ります。不要な場合は別途削除します。

## 付録：L0・L1 の作り直しと切り替え（復旧用）

L1 は共通項目を列として定義し、個別の内容を属性として保存するため、作り直すことはほとんどありません。
次の手順は、解析の誤りを直すとき、L1 の型や並び順を変えるとき、パイプそのものを替えるときの復旧用です。

### A1 派生列の追加

書き込み先に `ADD COLUMN` してから、MV を `ALTER TABLE ... MODIFY QUERY` で差し替えます。
順序を逆にすると、MV が存在しない列を作ることになります。

`MODIFY QUERY` は SELECT 全体を置き換えるので、MV の SELECT 全文を Git で管理します。
差し替えの境目を後から追えるよう、`ParserVersion` を上げます。
検証では、1 回の INSERT の中で新旧の版が混ざることはありませんでした。

既存の行の新しい列は既定値のままです。
過去のデータにも値が必要な場合は、L0 の保持期間内に限り、A2 で作り直します。
400 日分のデータに `MATERIALIZE COLUMN` を実行すると、大量のデータを更新するミューテーションが発生するため、避けます。

### A2 パーサの修正と過去日の作り直し

修正そのものは A1 と同じく `MODIFY QUERY` で行い、修正時刻以降の行から正しくなります。
修正前の日は、L0 から作業用テーブルに作り直し、日単位で `REPLACE PARTITION` します。

- **`REPLACE PARTITION` は下流の MV を発火させません。**
  L1 を置き換えても、分単位の集計テーブルは古い値のままです。
  集計テーブルの同じ日のパーティションも、作り直した行から集計して置き換えます。
- **`INSERT ... SELECT` は列を位置で対応付けます。**
  MV は列を名前で対応付けるので、MV の SELECT をそのまま貼ると列がずれます。
  型が異なれば変換エラーで止まりますが、型が同じ列同士なら値が入れ替わったまま成功します。
  MV の SELECT をサブクエリで包み、外側で書き込み先の列を表の順に並べます。
- **L0 には Pub/Sub の再配信がそのまま残っています。**
  L0 を読む段で `LIMIT 1 BY _message_id` を挟みます。
  挟まなかった検証では、8 分間の範囲で 493 件の重複が L1 に戻りました。
- **`REPLACE PARTITION` は対象日の既存データを丸ごと置き換えます。**
  遅延到着が落ち着いた日にだけ使い、当日には使いません。
  遅延到着の分布は `verify/checks.sql` の 4 番で測れます。

### A3 型、ORDER BY、PARTITION BY、エンジンの変更（Blue/Green）

新しいテーブル `gcl_logs_v2` と、境界時刻 T 以降のデータだけを書き込む MV を作ります。
境界には `_publish_time` を使います。

`_publish_time` は Pub/Sub がメッセージを受け付けた時刻なので、INSERT より必ず前にあります。
新しい MV を T より前に作っておけば、`_publish_time` が T 以降のメッセージはすべて新しい MV の作成後に INSERT されます。
T より前のメッセージは、遅れて届いても旧 MV が旧テーブルへ書きます。
T は作成時刻の 5〜10 分先にします。

LogEntry の `timestamp` は保持期間内の過去値と最大 24 時間先の未来値を取りうるので、境界には使えません。

バックフィルは作業用テーブルに作ってから `MOVE PARTITION` で移します。
`MOVE PARTITION` は移動先の既存データを消さないので、T 以降の行がすでに入っている日でも使えます。
ただし `MOVE PARTITION` も下流の MV を発火させないので、v2 の集計テーブルには作業用テーブルから集計した行を先に入れます。
遅延到着のログは過去の日付のパーティションに入るので、作業用テーブルにできたパーティションをすべて移します。
検証でも、T より前の約 20 分間のログをバックフィルした範囲が 2 日のパーティションにまたがりました。

型や列を変える場合、バックフィルの元は L0 にします（保持期間内に限ります）。
旧テーブルから変換すると、旧テーブルにない値は作れません。

読み取り先は、ClickStack ではソース設定のテーブル名で、SQL の利用者には名前を固定したビュー（`CREATE OR REPLACE VIEW gcl.logs`）で切り替えます。
ビュー経由でも、主キーとテキストインデックスによる絞り込みが使われました。

旧 MV を止めるまでは旧テーブルにも書き込みが続くので、読み取り先を戻すだけでロールバックできます。
その間は書き込みが二重になり、挿入の CPU とストレージが増えます。

### A4 ClickPipe 自体の変更

作成後に変えられない設定（サブスクリプションのフィルタなど）を変えるときは、新しいパイプを作って並走させます。
新しいパイプは新しいサブスクリプションを作り、そこには全メッセージのコピーが届きます。

新しいパイプは境界時刻 T2 より前に、開始位置 latest で作ります。
新しいサブスクリプションは作成後に公開されたメッセージをすべて受け取るので、T2 以降の分は取りこぼしません。

Pub/Sub トピックのメッセージ保持は、既定では有効にしません。
保持を有効にすると、公開された全メッセージに保持期間分の保管料（$0.27/GiB・月）がかかります（1 日 1.5 TiB を 7 日保持すると月 約 $2,900）。
再処理に使う元データはすでに L0 に保存しているので、役割も重なります。

新しいパイプの作成が T2 に間に合わなかったときだけ、`--seek-type timestamp` で T2 より前の時刻から読み直させます。
検証では、指定した時刻ちょうどから読み始めました。
この場合は作業を始める前に短い保持（例：1 日）を有効にし、終わったら外します。
保持を有効にする前のメッセージには Seek できません。

手順は Blue/Green と同じく境界時刻 T2 で分担します。
新しい着地テーブルから T2 以降のデータを書き込む MV を作り、旧 MV は `MODIFY QUERY` で T2 より前に絞ります。
Seek で遡った場合、その分には重複が混ざりますが（検証では 500 件）、すべて T2 より前なので境界条件によって除外されます。

旧パイプは、旧着地テーブルが T2 を越え、処理が停滞したバッチがないことを確かめてから止めます。
削除はロールバック期間の後にします。

### A5 `_publish_time` を持たない既存パイプラインからの移行

旧着地テーブルに `_message_id` と `_publish_time` がない場合、境界時刻で分担する A3 と A4 は使えません。
代わりに、LogEntry の識別子 `(logName, insertId, timestamp)` と、`_publish_time` の代用としての `receiveTimestamp` で切り替えます。
実ログでは、`receiveTimestamp` から Pub/Sub の公開までの差は 0.2〜2.4 秒でした。

1. 同じトピックに新しいパイプを `--seek-type latest` で作り、新しい構成で取り込みを開始する。最初に届いた `_publish_time` を T_new とする。
2. 旧着地テーブルのうち、`receiveTimestamp` が T_new の 10 分前より古い行を、新しいパーサでバックフィルする。旧着地テーブルにも再配信の重複があるので、LogEntry の識別子で除く。
3. 残りの前後 20 分ほどは、新しいパイプが書いた行と識別子で突き合わせ、ない行だけを入れる。
4. 新旧が並走している間に、受信時刻の 1 時間ごとに識別子の集合を突き合わせ、差が 0 であることを確かめる。
5. 読み取り先を切り替え、旧パイプを止める。旧テーブルはロールバック期間が過ぎてから削除する。

この手順のバックフィルは通常の INSERT なので、集計の MV も発火し、集計テーブルは自動で整合します。

SQL を生成してバックフィルするときは、MV の本文の `FROM` が旧着地テーブルに置き換わったことを生成時に検査します。
検証では置き換えが 1 か所漏れ、別の着地テーブルの行が混入しました。
INSERT の後に `system.query_log` の `tables` 列で読み取り元を確認すると、意図しないテーブルからの取り込みを検出できます。
